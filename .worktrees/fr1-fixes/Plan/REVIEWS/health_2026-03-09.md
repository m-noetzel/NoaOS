## Greatest Risk
The iOS package remains a library with no `@main` entry point. All 72 Swift tests pass in isolation, but no test or build step verifies that the components wire together into a runnable app. The ChatViewModel, AuthViewModel, and ChatService have never been exercised as an integrated unit -- each is tested with its own mocks. This is the RC1 pattern from the project audit ("tests validated shape, not behavior") replaying at the iOS layer. The first real app build (iOS11 or whenever an app target is created) may surface wiring failures that the current test suite cannot detect. This is the single biggest risk because it compounds with every iOS phase that adds more components without integration verification.

## Decisions Needed
- Schedule creation of an iOS app target (@main struct + dependency wiring) either as a standalone task or as part of iOS6. Every additional phase without an app target increases the risk of discovering wiring failures late.
- Decide whether the 14 pre-existing backend test failures warrant a fix phase before Wave 15C, or accept them as permanent technical debt.

## Risks You Are Taking
1. **No iOS app target (high impact, certain when app is built):** All iOS components exist as library code with no @main entry point. The first real app build will be the first integration test. Every phase that adds components without an app target deepens this gap. This is the RC1 replay risk.
2. **14 pre-existing backend test failures (low impact, certain):** These have persisted across 5+ waves. They erode trust in the test suite and make it harder to distinguish new regressions from old noise. None are in the iOS5 scope.
3. **3 BLE001 (blind-except) ruff violations remain in src/ (low-medium impact, low likelihood):** These are pre-existing. ruff reports 5 total violations (3 BLE001, 2 F401). The blind excepts may silently swallow runtime errors in production.
