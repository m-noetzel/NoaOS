## Patterns Identified

### Pattern 1: Test Maintenance Lag During Refactoring Waves (P1 -- watch list, single occurrence)

**Occurrences:** 1 wave (W23). No prior wave had this exact pattern at this scale (31 tests across 16 files).
**Category:** testing
**Current mitigation:** No specific gate. CI-023 (pre-phase test plan) is NOT EFFECTIVE (0% compliance across 3 waves). The existing M1/M2 QA gates check that tests exist and pass, but they review per-phase -- they do not catch cross-phase test breakage from a refactoring wave where Phase N breaks tests that were passing for Phase N-2.
**Root cause:** Wave 23 was a cross-cutting refactoring wave. Individual phases (CQ1-CQ8) each changed contracts (event sequences, model defaults, settings schema, API signatures) but test updates were deferred. The system-auditor caught the 31 failures at wave boundary, not during individual phase QA.
**Assessment:** This is the first occurrence of this specific pattern (large-scale test breakage from refactoring). Placing on watch list. If a future refactoring wave repeats this, it warrants a P1 proposal for mandatory cross-phase test validation during refactoring waves.

### Pattern 2: Hollow Migrations (P4 -- meets evidence threshold)

**Occurrences:** 3 waves within last 5 (Wave 14B QC1 C4, Wave 18 TM2, Wave 23 CQ9). 2 occurrences within the last 3 waves: TM2 (nullable `function_name` in DB, migration but no code update) and CQ9 (migration 019 adds `tool_name`/`function_name` but `_create_approval()` never populates them).
**Category:** architecture
**Current mitigation:** M7 (wiring completeness) checks that services/routers are wired. CI-042 (dead-end store detection) checks that stored fields have consumers. Neither explicitly covers the case where a migration adds columns but the write path never populates them.
**Gate gap:** CI-042 covers "stored but never read." Hollow migrations are the inverse: "schema exists but never written." This is a **missing gate** -- neither CI-042 nor any existing checklist item catches "migration adds column, write path does not populate it."

### Pattern 3: M5b Catches FINDINGS.md Drift (P3 -- gate working)

**Occurrences:** W23-audit-fix Cycle 1 FAIL was caught by M5b. This is the gate working as designed. CI-013 (M5b) has been effective since Wave 19 (5 consecutive waves of correct enforcement).
**Assessment:** No action needed. The gate is working. The audit-fix phase omitted FINDINGS.md updates, QA caught it on Cycle 1, it was fixed on Cycle 2. This is the system functioning correctly.

### Pattern 4: Signal Log Completeness Gap (P7 -- meets evidence threshold)

**Occurrences:** 2 consecutive waves (W22 FR1-FR4: 4 missing rows, W23 CQ1-CQ9: 9 missing rows). 13 phases across 2 waves without signal log entries.
**Category:** process
**Current mitigation:** CI-044 was proposed in Wave 22 analysis but has status DEFERRED.
**Assessment:** This is a recurring gap that CI-044 already addresses. The evidence threshold is now met (2 consecutive waves, 13 total missing rows). Recommending CI-044 be promoted from DEFERRED to PROPOSED with updated evidence.

## Proposals

### CI-045: Hollow Migration Detection Gate (M7 extension) (P2)

**Evidence:**
- Wave 18 TM2: `function_name` column added to approvals via migration but code path never populated it (review note in TM2 QA)
- Wave 23 CQ9: Migration 019 adds `tool_name`/`function_name` columns. `_create_approval()` in chat.py:875-883 constructs `Approval()` without setting these fields. Both values are available at lines 863-864 but not passed to the ORM constructor. (review_CQ1-CQ2-CQ9.md lines 67, 141-142)
- 2 occurrences across the last 3 waves (W18 TM2, W23 CQ9), same column family

**Not a duplicate of:** CI-042 (dead-end store detection). CI-042 covers "stored but never read" -- fields that are written to the DB but have no consumer. CI-045 covers the inverse: "schema exists but never written" -- migration adds columns but the write path does not populate them. Different failure direction, same wiring completeness category.

**Estimated impact:** medium -- prevents hollow migrations that create columns always NULL in production. Each occurrence wastes a migration slot and creates future confusion about whether the column is populated.

**Implementation burden:** low -- one additional bullet in the M7 section of QA_CHECKLIST.md.

**Confidence:** medium -- clear pattern (2 occurrences, same column family even), but the scope of the problem is narrow (migration-specific).

**Proposed change:** Add to QA_CHECKLIST.md M7 (Wiring Completeness), after the CI-042 bullet:

```markdown
- [ ] **CI-045**: When this phase adds a new DB migration with new columns: verify the application write path (ORM insert/update) populates those columns with actual values. A migration that adds a column but never writes to it is a hollow migration. Check: grep for the column name in ORM model constructors and update statements.
```

**Target:** Plan/QA_CHECKLIST.md (M7 section)
**Priority:** P2 (prevents wasted migrations and NULL columns, but not a blocking quality issue)

### CI-046: Signal Log Completeness Enforcement -- Promoted from CI-044 (P2)

**Evidence:**
- Wave 22: FR1-FR4 (4 of 6 phases) missing signal log rows (analysis_2026-03-14_wave22.md line 127)
- Wave 23: CQ1-CQ9 (all 9 phases) missing signal log rows (signals.md has zero CQ entries)
- 2 consecutive waves, 13 total missing rows. CI-044 was proposed at P3 in W22 but DEFERRED.

**Not a duplicate of:** CI-044 is the original proposal. CI-046 is a promotion with updated evidence (2nd consecutive wave of missing rows). CI-044 should be marked SUPERSEDED by CI-046.

**Estimated impact:** medium -- signal log is the CI agent's fast-scan prioritization tool. Without it, the CI agent must read all reviews from scratch. 13 missing rows across 2 waves degrades the efficiency of the CI analysis pipeline.

**Implementation burden:** low -- add one sentence to CLAUDE.md QA Review gate description.

**Confidence:** high -- clear recurring gap (2 consecutive waves, 100% missing rate in W23).

**Proposed change:** Add to CLAUDE.md Gates section, under "QA Review (MANDATORY)":

```markdown
- **Signal log row (mandatory)**: After every QA verdict, append one row to `Plan/CI/signals.md` with phase, date, verdict, and summary of key issues. Missing rows are a pipeline violation (same class as skipping FINDINGS sync).
```

**Target:** CLAUDE.md (Gates section, QA Review)
**Priority:** P2 (process improvement that enables CI efficiency; 2 consecutive waves of 100% missing rate meets threshold)

### CI-047: Refactoring Wave Cross-Phase Test Validation (P3)

**Evidence:**
- Wave 23: 31 tests across 16 files broken by CQ1-CQ8 code changes. Tests not updated alongside code. Discovered only at wave-boundary system audit. Required dedicated audit-fix phase. (audit_wave23_2026-03-18.md lines 106-125)
- Single occurrence, but high severity (31 tests, audit-fix phase required)

**Not a duplicate of:** CI-023 (pre-phase test plan) targets individual phase test planning. CI-047 targets cross-phase test breakage during refactoring waves where Phase N changes contracts that Phase N-2 tests depend on. Different scope (wave-level vs phase-level).

**Estimated impact:** medium -- avoids dedicated audit-fix phases for test maintenance. A refactoring wave that breaks 31 tests and requires a cleanup phase is ~1 extra QA cycle.

**Implementation burden:** medium -- requires adding a wave-level step that runs the full test suite after each phase in a refactoring wave (not just the phase's own tests). This adds runtime to each phase's verify gate.

**Confidence:** low -- single occurrence. Refactoring waves are infrequent. The cost of the gate (full test suite per phase) may exceed the cost of the occasional audit-fix phase.

**Proposed change:** Add to CLAUDE.md Implementation rules:

```markdown
- **Refactoring wave test check**: In waves whose primary purpose is refactoring or code quality (not new features), run the full unit test suite (`pytest tests/unit/`) after each phase's code changes, not just the phase-specific tests. Fix any broken tests in the same phase that broke them.
```

**Target:** CLAUDE.md (Implementation rules section)
**Priority:** P3 (nice to have -- single occurrence, medium implementation burden, low confidence)
