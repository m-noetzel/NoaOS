## Greatest Risk
The iOS authentication layer has no test for what happens when token refresh fails. If the backend rejects a stale refresh token, `AuthService.refresh()` throws but does not clear the Keychain. On next app launch, the stale token triggers `isAuthenticated = true` followed by an immediate failed refresh, creating a brief "logged in" flicker before the user is sent to LoginView. This is the exact pattern from the project audit (RC1: "Tests validated shape, not behavior") -- the happy path works perfectly, but the error path has untested behavior that degrades UX. The fix is small (clear Keychain on refresh failure, add one test), but it needs to happen before iOS5 builds on top of this auth layer.

## Decisions Needed

- The 14 pre-existing backend test failures continue to accumulate across waves. Schedule a fix phase or formally accept them.

## Risks You Are Taking
1. **Stale tokens on refresh failure (medium impact, moderate likelihood):** If the user's refresh token expires or is revoked, old tokens persist in Keychain causing a confusing momentary "logged in" state on app launch. Not a security risk (stale tokens are rejected by the backend), but a UX defect.
2. **14 pre-existing backend test failures (low impact, certain):** These have persisted across 4+ waves. They indicate test rot and reduce confidence in the test suite as a regression safety net.
3. **No app entry point (low impact, deferred):** iOS code is a library package with no @main struct. Until iOS5 creates the app target, all iOS components are tested in isolation only. This mirrors audit pattern RC6 (local optimization without system-level verification).
