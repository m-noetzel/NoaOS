## High Findings (fix soon)

### W22-H1: Agent limit settings are dead-end stores (not consumed by orchestrator)

**Severity:** High
**Files:** `src/noa/settings/models.py:85-87`, `src/noa/api/v1/settings.py:57-59`
**Description:** The FR6 settings fields `max_tool_calls`, `max_retries`, and `timeout_seconds` are stored in the DB and served by the settings API, but the orchestrator (`src/noa/orchestrator/`) never reads them. A `grep` for these field names in the orchestrator directory returns zero matches. The user can configure "max tool calls = 5" in the UI but the agent will ignore it completely.

This violates the "no dead-end stores" rule: data is stored but nothing reads it. The UI presents these as functional governance controls but they have no effect.

**Impact:** Users believe they have agent execution limits configured but the agent runs unconstrained. This is a UX honesty issue -- the controls are misleading.

**Fix:** Wire these settings into `OrchestratorRunner.run()` or the graph's tool-loop cap logic. Load from `SettingsRepository` at run start and enforce limits during graph execution.

### W22-H2: `approvals_enabled` setting is a dead-end store (not consumed by policy engine)

**Severity:** High
**Files:** `src/noa/settings/models.py:82-84`, `src/noa/api/v1/settings.py:55`
**Description:** The FR6 `approvals_enabled` toggle is stored in settings but neither the policy engine (`src/noa/policy/`) nor the orchestrator reads it. The user can toggle "Human-in-the-loop approvals" off in settings but all approval flows continue to fire.

A `grep` for `approvals_enabled` in both `src/noa/policy/` and `src/noa/orchestrator/` returns zero matches.

**Impact:** Same as H1 -- misleading UX control. User thinks they disabled approvals but the system ignores the toggle.

**Fix:** Wire into `PolicyEngine.evaluate()` or the orchestrator's approval check. When `approvals_enabled=False`, skip approval requests for non-critical risk tiers.

## Medium Findings (track)

### W22-M1: Runs and Cost endpoints do not filter by domain (FR1 gap)

**Severity:** Medium
**Files:** `src/noa/api/v1/runs.py:34-41`, `src/noa/api/v1/cost.py:100-121`
**Description:** The threads endpoint correctly filters by `privacy_mode` domain (FR1, line 58: `Conversation.domain == privacy_mode`), but the runs and cost endpoints show all data regardless of domain. When a user is in private mode, they can see costs and run details from external-domain conversations.

This is an incomplete application of the FR1 domain isolation pattern. Threads and messages are properly isolated; runs and costs are not.

**Impact:** Information leakage across domains. Private mode users can see external run costs and vice versa. For a single-user system this is cosmetic, but it violates the domain isolation principle.

**Fix:** Add `privacy_mode` query parameter to `/api/v1/runs` and filter `Run.privacy_mode == privacy_mode`. For cost, join through `UsageStats -> Run -> privacy_mode` or add a `domain` column to `UsageStats`.

### W22-M2: No Pydantic validation constraints on agent limit fields

**Severity:** Medium
**Files:** `src/noa/api/v1/settings.py:57-59`
**Description:** `max_tool_calls`, `max_retries`, and `timeout_seconds` in `UpdateSettingsRequest` have no `Field(ge=1)` or similar constraints. A user can set `max_tool_calls=-99` and it persists to DB without error. This was already noted in the FR6 QA review (S1).

**Impact:** Semantically invalid values accepted. When/if the orchestrator eventually reads these, negative values could cause unexpected behavior.

**Fix:** Add Pydantic `Field(ge=1, le=1000)` for `max_tool_calls`, `Field(ge=0, le=20)` for `max_retries`, `Field(ge=10, le=3600)` for `timeout_seconds`.

The governance settings added in FR6 (`approvals_enabled`, `max_tool_calls`, etc.) are not wired to the orchestrator. This means:

- The orchestrator graph still uses hardcoded defaults for tool loop caps.

The chat endpoint's domain isolation check (lines 120-131 in chat.py) correctly verifies thread domain before allowing chat. The SSE keepalive (FR4) is domain-agnostic, which is correct since keepalive is a transport concern.
