## Greatest Risk
**The 5 partially-resolved findings (H8, M5, M10, A1, A4) represent deferred architectural debt that compounds with each new feature wave.** H8 (in-memory rate limiting) means a process restart resets all rate limits. A1 (global mutable state) makes the codebase harder to test correctly. A4 (NoOpCheckpointer) means orchestrator runs cannot survive crashes. These are all "works in demo, breaks in production" issues. If iOS development (Wave 15) begins before addressing these, the production deployment surface doubles while the foundation remains fragile. The risk is not that any one of these fails catastrophically, but that their combination creates an unreliable system that erodes user trust after launch.

## Risks You Are Taking
1. **No lockfile for Python dependencies** -- pyproject.toml uses range pins (>=X,<Y). A dependency update could introduce breaking changes or vulnerabilities between builds. Likelihood: medium. Impact: build failures or subtle runtime bugs. Mitigation: generate and commit a pip-compile lockfile before production.

2. **In-memory rate limiting (H8) resets on restart** -- Any process restart (deployment, crash, OOM kill) clears all rate limit counters. An attacker could time requests around restarts to bypass limits entirely. Likelihood: low (single-user system). Impact: low for single-user, high if multi-user.

3. **NoOpCheckpointer (A4) means no crash recovery** -- If the orchestrator process dies mid-run, all state is lost. For long-running multi-tool tasks, this means silent data loss. Likelihood: medium (any OOM or timeout kills the run). Impact: medium (user must re-submit, losing context and incurring duplicate costs).
