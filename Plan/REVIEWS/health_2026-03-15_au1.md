## Greatest Risk

**Two open High findings represent dead-end stores (W22-H1/H2).** The `app.state.workers_degraded` flag is written at startup but never read by any endpoint or middleware — it cannot influence routing, health responses, or user experience. The thread `domain` column is populated by FR1 but the query layer in chat.py and threads.py does not filter by it, meaning domain isolation at the thread level is architectural scaffolding without enforcement. Both are High (not Critical) because they don't cause data loss or security holes — but W22-H2 in particular undermines the dual-domain isolation that is the project's core architectural invariant. If Wave 23 adds features that assume domain-scoped thread filtering is working, those features will behave incorrectly. These must be addressed before Wave 23 work that touches domain routing.

## Risks You Are Taking

1. **Thread domain filtering is unenforced (W22-H2, High, likely).** The `domain` column on threads is set by FR1 but chat.py and threads.py queries don't filter by it. Any Wave 23 feature that routes to private vs external based on thread domain will read the right column from the model but the query returns all threads regardless of domain. This is a latent isolation failure — it only bites when domain-specific features are actually used, but that usage is the project's next wave.

2. **No lockfile for Python dependencies (warn, low-medium probability).** Dependencies are pinned with `>=` + upper bounds but no lockfile (`poetry.lock`, `pip-compile` output, etc.). A transitive dependency could introduce a breaking change or vulnerability on a fresh install. This has been the state since Wave 1 and hasn't caused an incident, but it is a real risk for the Docker production build.

3. **AuthContext/AuthGuard startup behavior has no component-level test (low probability, low impact).** The AU1 fix for AUTH-H2 (startup /auth/me check) is correct and covered by a backend integration test, but the React component behavior (isLoading=true while pending, spinner render) has no Vitest/RTL test. If a future refactor breaks the loading guard, no test will catch it. Likely stable but worth a follow-up component test in a polish phase.
